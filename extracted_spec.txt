EdgeRetailAI — Computer Vision Improvement Criteria
SIH 26179 | YOLO26n | Edge-AI Retail Analytics POC
Assessment basis: the uploaded EdgeRetailAI repository, with emphasis on the current vision, inference, tracking, zone analytics, shelf classification, and Raspberry Pi deployment path.
1. Executive Summary
The software foundation is sufficiently mature for a POC: the repository has an ONNX Runtime inference seam, camera/inference decoupling, anonymous tracking, zone analytics, shelf classification, alerts, APIs, tests, and both FP32 and INT8 YOLO26n ONNX models. The main weakness is not the surrounding application architecture; it is the semantic quality of the computer-vision layer.
The current detector wrapper filters YOLO output to COCO class 0 (person). Consequently, the system is presently much closer to a shopper/footfall analytics system than a complete retail-vision system. Product detection, product interaction, shelf occupancy, stock estimation, and robust multi-class tracking should therefore be the primary CV work.

3. Target CV Architecture
The target should separate perception from analytics. YOLO26n should answer 'what is visible and where?', tracking should answer 'which observation belongs to the same anonymous object?', and analytics should answer 'what retail event does this imply?'
Camera → frame capture → latest-frame buffer
Latest frame → YOLO26n detector
Detections → class filtering + confidence policy
Person/product/cart detections → class-aware tracking
Tracks → zone membership + temporal state
Person + product/shelf spatial relationships → interaction events
Shelf/product observations → occupancy and stock state
Events → FastAPI/database/dashboard/alerts

10. What Should NOT Be Changed Yet
Do not rewrite the FastAPI/Svelte architecture merely because the CV layer is weak.
Do not move to a larger YOLO model before proving that YOLO26n + better data is insufficient.
Do not spend significant time on dashboard polish before CV event accuracy is measurable.
Do not treat the existing custom IoU tracker as a final production tracker; measure it first.
Do not use Canny edge density as the primary evidence for inventory claims if product detection is available.

12. Final Priority Assessment
The single highest-value change is to stop treating YOLO26n as a person-only detector. The second is to train and evaluate a retail-specific YOLO26n model. The third is to turn detections into temporal retail events—especially product interaction and shelf occupancy. Once those are reliable, tracking, queue estimation, and edge optimization can be tuned around measured behavior.
In practical SIH terms: prioritize CV correctness and demonstrable business events over adding more software modules. A smaller number of highly reliable analytics is more convincing than a dashboard containing many metrics whose underlying detections are weak.
Appendix A — Proposed CV Data Contract
Use a generic detection object throughout the vision pipeline:
Detection: 
class_id, class_name, confidence, bbox(x,y,w,h), timestamp
Track: 
track_id, class_id, bbox, confidence, age, last_seen, zone_id
InteractionEvent: 
track_id, product/shelf zone, start_ts, end_ts, confidence
StockEvent: 
shelf_id, status, occupancy, confidence, timestamp
Appendix B — Versioning
Every benchmark result should record: git commit, model filename/hash, model precision (FP32/INT8), image size, confidence thresholds, tracker settings, camera resolution/FPS, Pi hardware/software environment, and dataset version.
